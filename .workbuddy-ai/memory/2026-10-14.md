### 1. The About footer stopped echoing the hero

The Patch's footer reprinted `PROOF_READOUTS` — `4+ YEARS`, `3 PRODUCT TEAMS`,
`15K+ USERS` — which is exactly what the hero's proof strip prints in
`arrangement-mixer.tsx`. The panel was an echo of the section above it. Owner's
words: "content like 4+ years and etc its like we have used in hero section".

Replaced with an **output stage**: a finned heatsink, a speaker grille and a
power lamp, all `aria-hidden`, no text. `.bridge` / `.bounce` in
`patch.module.css` are gone; `.outStage` / `.outFins` / `.outGrille` /
`.outLamp` replace them.

Two things worth keeping in mind if this is revisited:

- The grille is a **dot matrix**, not bars. A row of bars reads as a meter,
  and a meter reads as a value — and `design.md` §0.0 says a control has to
  encode something real. Decoration must not look like a readout.
- The decoration is still honest: `.outFins` opacity and `.outLamp` colour are
  driven by `--settle` and `--p`, which are the panel's own power-on act. So
  `--patch-bounce` did **not** become an orphaned write — it now warms up the
  amp instead of filling a meter. The hook still writes the same six numbers.

`tests/patch-panel.test.ts`: `prints the hero proof strip unchanged` was
inverted into `does not reprint the hero proof strip` — it asserts no proof
*unit* appears anywhere in the panel, and that the footer is `aria-hidden` with
empty text. That is the real contract now: the page says a thing once.

### 2. The LCD got a screen

`.lcd` was a flat `#101315` rectangle, which reads as a hole in the panel
rather than a screen. Now a layered static background: scanlines at 3px pitch,
a 24px phosphor grid, and a soft green wash from the top edge, over the same
base colour. Alphas all under 6% so the 14–17px body copy loses no contrast.
Static on purpose — an animated pattern is a repaint every frame, and the rule
on this page is that nothing moves while nothing is happening.

The hero's own `.lcd` (the 26px toolbar strip in `arrangement.module.css`) was
deliberately **left alone**: it carries 8px text, and a scanline pattern at
that size hurts legibility more than it helps.

### 3. The skills knobs are now the Patch's knobs

`rack-01/primitives.tsx`'s `Knob` was a bright silver milled disc inside a
dotted scale ring. The Patch's `Knob` (`components/patch/patch-kit.tsx`) is a
dark cap with one coloured index line and no ring. Owner wanted them matched.

Done: `.knob` is now `radial-gradient(circle at 35% 30%, #4a4f55, #1d2125 70%)`
with the same inset highlights, `.knob span` is a 2px `--signal-orange` line,
and **every `.knobScale` rule is deleted** — including four media-query
overrides and the `<div className={styles.knobScale}>` in the primitive.

The one deliberate difference: the skills knob is a **real input**
(`role="slider"`, drag, arrows, Home/End) while the Patch's are readouts. Same
part, same look, different contract. The look is what was asked to match; the
contract must not be copied across.

Both faces are cream, so a dark cap reads on the skills controller
(`linear-gradient(145deg, #e9e6df, #c3c0b9)`) exactly as it does on the Patch.

## The contact heading was invisible in the default theme

Owner: "text on 'Bring me the difficult part.' make it black in contact section."
Not a preference — a real bug, and a good one to have on the record.

`.contact` sits on `var(--chassis)` (cream `#e7e2d8` in light, graphite
`#23262a` in dark). The `<h2>` in `.contactFreshHeader` set no colour of its
own, so it inherited `--room-ink` from `.root` — and `--room-ink` is
`#f1eee5`, deliberately the **same cream in both themes**, because the device
wall does not daylight. So on the contact section's cream chassis the largest
type on the page was cream on cream.

**The default theme is light** (`app/layout.tsx:188`, `defaultTheme="light"`),
which is why this was visible to the owner and not just a dark-mode curiosity.

Fix, in the contact-ink block near the other `--panel-*` rules:

```css
.contactFreshHeader .sectionHeading h2 {
  color: var(--panel-ink);
}
```

`--panel-ink` is `#101211` in light (black to the eye) and `#f1eee5` in dark,
so it follows the surface the way `.contactFreshHeader > p` already did. My
rule is the last one matching that selector, so it wins the cascade outright —
verified by grep, not assumed.

**Worth remembering:** any text placed directly on a `--chassis` surface must
set its own colour. `--room-ink` is the floor's ink and does not flip; it will
silently be wrong on any themed panel.

## The same bug's twin: the "Open channel" eyebrow

Owner: "Open channel make it black". Same root cause as the heading, one level
down. `.sectionHeading > .silkscreen` sets `color: #ffffff` for every section
on the dark floor; the contact header's eyebrow inherited it and sat white on
cream. Folded into the same rule as the h2:

```css
.contactFreshHeader .sectionHeading h2,
.contactFreshHeader .sectionHeading > .silkscreen {
  color: var(--panel-ink);
}
```

The `06` stays orange — `.sectionIndex` colours itself, so only the words
follow. The eyebrow's hairline is `currentColor`, so it darkens with the text
instead of staying a white rule on a cream band.

**This bug class had already been found once and fixed in one place only.**
`.contactBriefHead > .silkscreen` (line ~7367) carries the comment: *"The
silkscreen base rule ends in `color: #ffffff`, which was invisible on this
cream band."* So someone hit it for "Before you write" and did not look for
siblings. If a third instance turns up, the real fix is to stop hard-coding
`#ffffff` in the base `.silkscreen` rule and make it `currentColor` with the
dark-floor sections opting in.
