## Fourth round: commit `1e4893b` (chapter devices read as static)

User: *"the device in group 01 INTERACTION until 03 PRODUCTION in about section
prev (before enchant to 3d) has animation movement but current is like static and
movement not smooth"*. Second time they reported this. Found **two** real defects.

### A. The glass canvas could take over from a scene that never animates

`GlassDevice` had **no gate**. Every scene's motion is gated on a media query
(`BENCH_QUERY` = min-width 769 + **min-height 700** + reduced-motion no-preference),
and the hook is what writes `--p`. On a 640px-tall viewport, or with
`prefers-reduced-motion: reduce`, the hook never runs — but the canvas still
attached, set `data-glass="on"`, and that attribute *hides the CSS solid and
switches off the CSS tilt that poses it*. Result: a dead canvas frozen on the
three.js `REST` pose (sampler `rx:-14,ry:20` — **not** the CSS `--p:0.5` pose
`rx:35`), where the stylesheet had authored a composed resting frame.

Reproduced exactly: at 1440x640 and at 1440x900+reduce, `benchMotion:(unset)`,
`p:(unset)`, `glassAttr:"on"`, `tilt:"none"`, canvas 0 frames changed over 960px.

Fix: `GlassDevice` takes a `gate` prop (the scene's own query) and only takes over
while it matches; new `features/landing-page/components/motion-gate.ts` exports
`BENCH_QUERY` / `BRIDGE_QUERY` (previously module-private in the two hooks) and all
three callers pass theirs (`bench-chapters.tsx`, `bench-device-layer.tsx` →
BENCH_QUERY; `skills-bridge.tsx` → BRIDGE_QUERY). The attach path also needed a
generation counter so an `attachGlass` resolving after the gate closed can't put
`data-glass` back. `.stage:has([data-glass='on']) .tilt` additionally scoped under
`[data-motion='ready']` to cover "query matches but the GSAP import failed".

### B. The arc was bound to the chapter's travel, not to its pin

`bindReading` used `start:'top 85%'`, `end:'bottom 30%'` → 139svh. But `.visual`
is `position:sticky; top:26svh; height:48svh` inside an 84svh `.chapter`, so the
pin is only `chapterH - visualH` = 36svh. **~74% of the rotation played while the
device was climbing into frame or already leaving it**; the part a reader watches
(held still, centred) was the remaining 26%. That is why it read as barely moving.

Fix: bind to the pin — `start:'top 26%'` (the sticky offset) and `end:'bottom 74%'`
(that offset + the visual's height). Both are the stylesheet's own numbers, so the
binding survives a chapter-height change: `end` reduces to `stickyTop + visualH`
regardless of `chapterH`. Measured: pin window chapterTop 234 → −198 and `--p` in
(0,1) across exactly those rows, 0 on approach, 1 on exit.

Also raised `.chapter` min-height 84svh → **96svh** so the pin is 48svh (≈430px)
not 36svh. Deliberately not more: `--bench-runway` is measured from the About panel
and both are in flow, so **each svh added here costs the document two** — 104svh
was +1.2 viewports for another 70px of pin. 96svh is +0.72 viewports.

## Fifth round: commit `1f2c94f` (render budget + arc range) — the real cause

User: *"still not good movement in device its not consistent sometimes is work
sometimes is cannot, i think the componen was render on scene i begin with the
interaction... and on divider black hole why not use the same component your job
is improve or enchant movement animation scroll and its start movement when

Their hypothesis was **right**, and it was the renderer's draw budget.

### The starvation

`glass-devices.ts` draws at most `BUDGET = 6` devices a frame and it walked
`controllers` **from the front every frame**. Six flying devices sit in the
About's stage *behind* the chapters and are registered first. From chapter 1
onward they are faded to nothing (`--o: 0`) but were still `visible`, still
`dirty`, still first in the set — so they ate all six slots and the three
chapter devices, added last, **never drew at all**.

Instrumenting `CanvasRenderingContext2D.prototype.drawImage` (the device canvas
is a 2D blit, so this counts real renders per device) over a full scroll of all
three chapters:

```
before:  chapter devices  3 draws: [ 0, 0, 1 ]    flying devices  214 each
after:   chapter devices  3 draws: [ 85, 132, 135 ]
```

That is exactly the "sometimes works, sometimes cannot" — it depended on how
many flyers happened to be live.

Two fixes, both needed:

1. `schedule()` is now **round-robin** over `[...controllers]` with a
   module-level `cursor` that resumes where the budget ran out.
2. `GlassPose` gains **`alpha`** (the host's opacity). Flyers pass
   `flight.opacity`, the bridge passes `device.opacity`; a controller at or
   below `0.001` is marked `hidden` and skipped. The cursor alone would still
   spend slots on invisible flyers.

Flying devices did not regress: each still draws on essentially every frame it
is opaque (delta of 1 per opaque frame, 72–155 total) and **zero** while not.

### The arc now spans the device's visible life

`'top 85%'/'bottom 30%'` → `'top 26%'/'bottom 74%'` (previous round) → now
**`'top bottom'` / `'bottom top'`**. The sticky-window range held the device
*perfectly still* for the 666px it took to climb into the pin — the first thing
a reader sees of it — so it read as a still object that then lurched. The
original range had the opposite fault (74% of the tumble off-frame). With the
new range `--p` is 0 only while the device is off screen and 1 only once it has
left, which is literally "start moving when the component comes into view".
Measured: range 5791 → 7447 (1656px) for `chapterH` 756; `p=0.000` at
`visualTop 900` (off screen), `p=1.000` at `visualTop -432` (off screen), 10/10
sampled steps moving, theta swing 1.2008 rad.

`.chapter` reverted `96svh` → **`84svh`**: the arc no longer depends on the pin,
and every svh there costs the document two (the runway is measured from the
panel with both in flow). Doc height back to 19667 = 21.85 viewports (was 22.57).

### Answer to "on divider black hole why not use the same component"

It **already does**. `skills-bridge.tsx:86` renders the identical
`<GlassDevice kind gate={BRIDGE_QUERY} fallback={<Device/>} />`, and
`BRIDGE_DEVICES` ids are `sampler | cassette | vinyl` — the same three kinds,
same three.js models, same shared offscreen renderer, same `setGlassPose`
registry, and now the same `alpha`. What is *not* shared is the **driver**, and
that is deliberate — the choreography is different, not the component:

- `chapterPose(kind, p)` (`glass-registry.ts`, ~6 lines) is a linear restatement
  of the CSS `.tilt` calc. **Rotation only** — a chapter device turns in place
  and never leaves its box; CSS positions it via the sticky grid.
- `bridgeFrame(p, w, h)` (`skills-bridge-frame.ts`, ~70 lines) owns the px
  **position**, scale, opacity, sway, the polar spiral fall (radius shrinks
  while the angle turns 3.4π) *and* the sheet mask / horizon / core glow. Its
  devices fly in from off-sheet, hover, then fall into the hole.
- A bridge device is positioned in **px from the stage's top-left** because the
  bridge owns that layout; a chapter device is positioned by CSS and the canvas
  is only handed a rotation. One `progress` → a whole frame for the bridge,
  versus a rotation for the chapter.

So the duplication is only the pose arithmetic, and collapsing it would mean
abstracting over two genuinely different motions. The bug the user actually hit
was in the **shared** layer (the renderer), which is why the bridge got the fix
for free.

Bridge verified after the fix: over its visible window (p 0.04–0.52) the three
devices drew 216 / 234 / 236 frames, silhouette theta changed on 19–25 of 27
steps, and `--o` matches the model exactly (1 from p≈0.05, sampler gone by
p=0.5, cassette 0.9878 at p=0.5 — matching `1 - smooth((fall-0.8)/0.2)`).
Invisible ones drew nothing. The CSS rotation on `.rot` is written only until
the canvas takes over and is then cleared by `setGlassPose` — confirmed live
(9900 → `rotateX(53.45deg)…`; 9960 onward → empty while the canvas kept
turning), so there is **no double rotation**.

Verification: tsc clean, eslint clean, **428/428 jest** (20 suites), 60fps
(p99 16.8ms, no frame >33ms). Pushed `d4be4a5..1f2c94f`; local `main` in sync.

## Tenth round: the "font size is too big" bug — a `:root` alias that resolves nowhere

User: *"adjust some text font size is too big example in skills section, experience and
project section for font size can you rollback to prev"*.

**Not a size regression.** `8ad255f` had rewired every `font:` shorthand across the landing
page from `var(--font-geist-mono)` / `var(--font-space-grotesk)` to the new
`var(--deck-font-{ui,mono,display,readout})` aliases — **167 usages across 10 CSS modules**
(rack-01 113, work 18, bench-chapters 10, arrangement 8, matter 7, bench 4, patch 4, kit 2,
skills-bridge 1). But `app/deck-theme.css` declared those four aliases on **`:root`**, and the
`--font-*` faces are injected by next/font on **`<body>`** (`app/layout.tsx:182`).

A custom property's `var()` is substituted on the element where it is *declared*, so
`--deck-font-ui` computed on `<html>` could never see `--font-space-grotesk` → the alias became
the **guaranteed-invalid value** → every `font:` shorthand reading it was **dropped** → the
element inherited the 16px body face instead of the 6–12px silkscreen the rule asked for.
Headings that asked for `clamp(39px,5vw,76px)` shrank; small labels ballooned.

**Proof (isolated, real Chrome):** a probe page with the alias on `:root` rendered
`font: 700 9px var(--a-deck-ui)` as **16px Times** with the custom property computing to `""`;
the same declaration with the alias on `body` rendered **9px Space Grotesk**.

**Fix:** moved the four aliases out of `:root` into their own `body { … }` rule in
`app/deck-theme.css`, with a comment explaining the constraint. Colour/shape/material tokens

## Round 12 — the docks shrink to 36px

Asked as *"reduce size Quick navigation"*. That string is only the `aria-label` of
`MagneticDock` (`features/layout/components/magnetic-dock.tsx`), not visible text — so the
target is the landing dock itself. Checked first that there are **two** docks and that the

The bar height is the icon box plus its padding, not an independent number: 36 + 4x2 = 44
(`h-11`) on mobile, 36 + 6x2 = 48 (`h-12`) on md. Set the height separately from the icon box
and the magnify ends up floating in dead space. Radii scaled with the boxes (nav 16 -> 12,
chip 12 -> 10, booth capsule 18 -> 14), because a fixed radius on a shorter capsule takes a
bigger share of each corner and walks it back toward the pill the booth dock deliberately
moved away from.
