# 2026-10-23

## The boot no longer arrives after the hero

`LandingGate` used to be the whole story: `showGate` starts `false`, an effect
sets it a frame after hydration, and the overlay lands on a page the visitor has
already read. The comment claimed the delay was "invisible"; it is one frame on
a fast machine and most of a second on a phone, and what it hides is the hero's
name already rising.

Fixed by splitting the boot into a server half and a client half:

- `StormCover` (exported from `signal-storm-preloader.tsx`) is the storm's own
  first frame — the bare ground, because the rows start at `opacity: 0`. It is
  in the landing page's HTML, so it is painted before React exists.
- The `<head>` script in `app/layout.tsx` writes `data-boot="on"` (which is what
  shows the cover; without the attribute it is `visibility: hidden`, so a no-JS
  visitor never sees it) plus `--boot-play: paused` for the hero's letters, and
  an 8s failsafe that withdraws both if the app never hydrates.
- The gate's state is now `cover | storm | done`, not a boolean. `storm` and
  `cover` are mutually exclusive, so the handoff is one commit and there is
  nothing to cross-fade: same class, same pixels.

`.ground`'s paint moved to `.groundPaint` so the cover and the storm's ground
read one declaration rather than two that can drift.

Also fixed: the dock's pre-hide script in `app/layout.tsx` used a top-level
`return` inside a classic `<script>`, which is a SyntaxError — the whole block
never ran. Rewritten as an `if`. Any inline head script added here must avoid
`return` at the top level.

Verified in Chrome: with every JS chunk aborted, first paint is the cover
(`data-boot=on`, 1440x900, hero fully hidden); a repeat visit shows neither the
cover nor the storm; reduced motion gets the cover without the letter pause and
`--boot-play` is left unset.

## The boot was too fast, so it is 2.52s now

User: "it too fast". The old 1740ms left only 300ms between the last row
arriving (600ms) and the merge taking it (900ms), so the one beat with content
in it — seven rows of studio words running — was never readable.

New `STORM_TIMELINE`: enter 420/45 (last row 690), **merge at 1500** (810ms of
nothing but running words), merge 520/34, fuse 1640/460, release 2050, ground
2100/260, band 2320/200, total 2520. The tail beats barely moved: that handoff
is what makes the boot end *in* the hero and was never the rushed part.

The test that pinned `total < 2000` now pins a band (`2200..3000`) and there is
a new guard that the run-before-merge gap is `>= 700ms` — that gap is the thing
that was wrong, so it is the thing to assert. Measured in Chrome: overlay lived
2556ms; the band frame shows the letters already risen under it.

## Still blinked: two ordering bugs, both only visible frame-by-frame

"still not smooth its like blinked to hero section". Two separate causes, and
neither was guessable from the code — both were found by sampling the DOM every
rAF and printing only the transitions.

**1. React's hydration commit strips `data-boot`.** `reactStrictMode: true`, and
independently of that, the hydration commit reconciles `<html>` and drops
attributes that are not in its props — which `data-boot` is not. Traced with a
MutationObserver: `on` at 313ms, **gone at 918ms**, back at 1061ms when the
passive effect ran. 143ms of hero. A `useEffect` is always one paint too late
for this; the fix is `useBootLayoutEffect` (`useLayoutEffect` in the browser,
`useEffect` on the server so SSR does not warn), which re-asserts inside the
same commit. The effect also *sets* the attribute when it should play rather
than assuming the script's value, so it is re-entrant — React's dev double-mount
runs the cleanup between the two invocations.

The cleanup's withdrawal is additionally deferred to `setTimeout(0)` and
cancelled by the next run, so a simulated unmount cannot withdraw state for a
frame while a real unmount still leaves nothing behind.

**2. The cover was the last element in the document.** It was rendered after
`{children}`, so in the streamed HTML it sat **136KB after the hero's name
clip** — 94% of the way through a 427KB document. The parser can paint while it
streams, so the hero was on screen for the whole parse and the cover landed on
top of it afterwards. Moving it before `{children}` puts it 2.5KB after
`<body>`; stacking is unaffected because it is `position: fixed` with a
z-index.

Verified in production (`next start`): 208 frames sampled, **0** with the hero
exposed before the storm, cover up at 187ms, storm at 736ms. Repeat visit: no
cover, no storm, straight to the hero. A frame sampler that checks
`cover || storm` is the only way to test this — a screenshot cannot tell you
what happened between two paints.
